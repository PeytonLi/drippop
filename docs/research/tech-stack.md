# Social-feed try-on: recommended stack and job architecture

> Preserved research from October 10, 2026. The [current PRD](../PRD.md) is authoritative where these notes contain provisional findings.

Checked 2026-10-10 using Context7 and current primary documentation. Research/recommendation only: no deployments, cloud-account actions, credentials, live generation calls or app implementation changes. Covers the accepted native Android overlay and its supporting backend. Three.js/3D is an explicit stretch feature to include in the future PRD; generated 2D previews form the first version.

## Recommendation

Use **one Python/FastAPI codebase**, deployed as a client-facing Cloud Run API and a private Cloud Run task worker. Add Firebase Authentication, Firestore job metadata, private Google Cloud Storage images, and Cloud Tasks for durable submission/status checks. This is a coherent small architecture: the phone's network request ends after accepting the job; the queue owns subsequent work. Google documents authenticated Cloud Tasks invocation of a private Cloud Run service and rate limiting calls to third-party APIs. [Cloud Run asynchronous tasks](https://docs.cloud.google.com/run/docs/triggering/using-tasks).

The two services can share one container image and repository, with API/worker startup modes exposing different routes. This is a recommendation, not a platform requirement. It keeps user authentication separate from Google service-account authentication without creating separate business backends.

For the first prototype, **upload/download images through the authenticated API**, rather than adding direct Firebase Storage access or signed URL plumbing. Keep the saved person photo in private Android app files; upload a temporary copy with each job. Cloud Storage remains private and backend-managed. Direct short-lived signed URLs are a later transport optimization; possession of a signed URL grants access until expiration, so issuing one still requires an ownership check. [Cloud Storage signed URLs](https://docs.cloud.google.com/storage/docs/access-control/signed-urls).

## Native capture and AI selection before generation

The native foreground service manages an explicitly authorized MediaProjection session and the floating panel. A Quick Settings tile starts/stops the session; the Try on bubble initiates one selected-frame analysis. Android 14+ can capture the chosen app instead of the entire display. Consent is required for each new session, and locking the screen or stopping projection invalidates it. Update the overlay and release capture resources when that happens. The foreground service is required for the capture workflow, not a guarantee that Android will keep an app process alive forever. [MediaProjection](https://developer.android.com/media/grow/media-projection), [Quick Settings](https://developer.android.com/develop/ui/views/quicksettings-tiles).

Proposal: pass the user-selected frame to the authenticated analysis endpoint, have Gemini return provisional person boxes, visible garments and category, and highlight those choices in the overlay. Gemini documents normalized object boxes and structured schema outputs; neither provides a guarantee that it will identify every social-feed garment correctly. Server validation must check coordinates/category, and the user needs a manual correction path. [Object detection](https://ai.google.dev/gemini-api/docs/image-understanding#object-detection), [structured outputs](https://ai.google.dev/gemini-api/docs/structured-output).

Retain enough of the selected wearer reference to satisfy YouCam's requirements. Its overview accepts worn outfit photographs, but requires appropriate pose, face visibility and sufficient unobstructed clothing for the chosen region. A tiny garment-only crop is not automatically a valid worn reference. Gemini supplies localization/category rather than a reconstructed flat garment; YouCam performs the actual visual transfer. A reel supplies a still captured frame for this first version. [YouCam input requirements](https://docs.perfectcorp.com/reference/ai_clothes).

Processing is cloud-based: the selected frame and personal image are sent off-device for these AI calls. Store transient cloud copies privately, enforce their owner's access and expiry, and transmit only frames deliberately selected by the user. Provider-side retention and data-use terms require review before a public release.

## Three.js stretch requirement for the PRD

Carry the user's explicit requirement into the PRD: **a rotatable 3D personal preview inside the existing expandable overlay**, with the 2D result remaining available on unsupported devices. Three.js can render imported scene/animation assets; the current WebGLRenderer requires WebGL2. Android can package local JavaScript and assets inside a WebView using WebViewAssetLoader. This establishes a candidate hosting approach, not verified performance inside this overlay. [GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html), [WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html), [Android embedded content](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content).

First prove the viewer with one compatible avatar and known garment assets. Then investigate obtaining a personal body model and reconstructing/fitting arbitrary social-image garments. Hidden garment details cannot be measured from the captured view. YouCam's documented 2D image result is not a rotatable mesh, and placing that image on a 3D plane does not establish an all-angle clothing preview. These are scope and feasibility distinctions to preserve in the PRD, rather than promising the stretch as part of the first release.

## Development order

1. On a physical Android phone, prove capture permission, current-frame capture, floating selection/progress/result UI and collapse back to scrolling, using a placeholder preview.
2. Integrate the authenticated backend and real YouCam processing with known suitable reference images. Verify authorization, job recovery and duplicate-request handling with small focused tests.
3. Add Gemini automatic selection plus manual correction, then test cluttered posts, video frames, multiple people, obstructed garments and unsupported captures.
4. Measure actual latency, reference acceptance and visible garment fidelity; use those observations to set progress/error behavior and supported-input claims.
5. Begin the bounded Three.js experiment only after the main same-feed experience works.

## Job and image sequence

The following is the proposed architecture after the user confirms a garment selection; the separate localization research will define the preceding capture/detection interaction.

1. **Identify:** Android signs in anonymously and sends its Firebase ID token with API requests. FastAPI verifies it and obtains the UID from the verified token, never a caller-supplied `uid`. Anonymous accounts still have an authenticated identity. [Verify ID tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens).
2. **Accept:** the phone supplies an idempotency key and selected garment/person images. API enforces ownership, file/image limits and paid-job limits, stores temporary bytes in private GCS, and creates the owner's Firestore job. A repeated key with the same inputs returns the same job; changed inputs under that key are rejected. This behavior is our design recommendation.
3. **Dispatch:** API enqueues a deterministically named submission task containing a job ID/phase, not image bytes or API credentials, and returns `202` with the job ID only after enqueue succeeds. Job state and task creation are not one atomic operation: record the pending dispatch, retry task creation with the same name, and heal that pending action when the original request is retried. A bounded reconciliation pass is appropriate later for abandoned dispatches.
4. **Submit:** Cloud Tasks calls the private worker with its Google OIDC token. Worker loads and transactionally claims the job, reads private input bytes, calls the provider, and persists the returned provider task ID before scheduling the first check. External network calls must happen outside Firestore transaction callbacks, which may rerun. [Authenticated Cloud Run task invocation](https://docs.cloud.google.com/run/docs/triggering/using-tasks), [Firestore transaction behavior](https://firebase.google.com/docs/firestore/manage-data/transactions).
5. **Check:** a scheduled task performs one short provider status query. If still processing, it persists a pending next-check action, ensures the next named task exists, then returns success. No sleeping loop holds the phone's request or relies on an instance after its response. Suggested check intervals/deadline are tuning choices to establish from provider limits and measured behavior.
6. **Finish:** when the provider reports completion, worker copies output into private GCS and marks the job successful only after that write succeeds. Deterministic output names/object preconditions let a retry reuse the saved result. Terminal provider failures become explicit failed jobs, not infinite polling.
7. **Display:** phone polls its authorized job endpoint and retrieves the image through an authorized API endpoint. It draws the result in the Android overlay. On restart/reconnect it can resume from the retained job ID; native overlay lifetime is a separate Android concern.
8. **Expire/delete:** a user deletion marks the job canceled/deleted first, blocks subsequent reads and worker writes, then deletes its images. A storage lifecycle policy cleans abandoned temporary objects; do not promise an exact deletion instant from lifecycle evaluation alone. [Object lifecycle](https://docs.cloud.google.com/storage/docs/lifecycle).

Firestore is the authority for job state. Cloud Tasks is dispatch, not the user's progress database. No client endpoint exposes the provider key or allows arbitrary job IDs/object paths to be fetched without checking the authenticated owner.

## Retry and access details that must survive implementation

**Cloud Tasks is at least once, not exactly once.** Duplicate executions and non-guaranteed execution order are documented. Named tasks, transactional claims, phase versions and terminal-state checks handle ordinary repeats, but task naming does not remove the need for an idempotent handler. Each task must ensure any persisted pending follow-up dispatch exists before acknowledging; otherwise a crash between database update and enqueue can strand a job. [Cloud Tasks pitfalls](https://docs.cloud.google.com/tasks/docs/common-pitfalls).

**Paid submission has an uncertainty window.** If the provider accepts a generation but the worker dies before saving its returned task ID, automatically resubmitting may charge twice. Firestore cannot atomically commit with an external provider. If provider-supported idempotency/reconciliation is unavailable, record `submission_unknown`, stop automatic resubmission and expose a recoverable failure. Distinguish that from safe retries of status GETs or result downloads. This is an architecture inference; provider idempotency support remains to be verified separately.

Set handler/network timeouts below task dispatch deadline, and cap retries and total job lifetime. HTTP target tasks have a maximum 30-minute dispatch deadline, but each proposed handler should finish far sooner. An HTTP timeout does not guarantee the worker stopped, so leases/phase checks still matter. [Task reference](https://docs.cloud.google.com/tasks/docs/reference/rpc/google.cloud.tasks.v2).

**Anonymous does not mean public access.** All create/read/download/delete endpoints verify tokens and compare `owner_uid`; anonymous sign-in can later link permanent credentials. Server Firestore clients bypass client Security Rules and use IAM, so rules alone cannot authorize FastAPI requests. With API-only database access, deny direct mobile Firestore reads/writes and perform authorization in the backend. [Anonymous linking](https://firebase.google.com/docs/auth/android/anonymous-auth), [server bypass caveat](https://firebase.google.com/docs/firestore/security/rules-conditions).

Use one Google service identity to invoke the private worker and grant only its `run.invoker` access; give runtime identities the required database/storage/secret/queue permissions. Keep authenticated-user routes on the client-facing API. UID quotas alone are not a strong spending boundary because anonymous users can obtain new identities: add project-wide paid-job limits, bounded queue concurrency and a controlled public-demo allowance. These limits are design choices, not automatic guarantees from Firebase Authentication.

## Simplifications and prerequisites

Do not add Redis/Celery, RabbitMQ, Pub/Sub, Cloud Run Jobs per preview, a SQL database, direct Firestore realtime listeners, WebSockets or a separate account-management backend for this first workflow. Cloud Tasks and Firestore cover durable dispatch/state; normal API polling covers the tray. API-mediated image upload/download is a simpler sound alternative to direct Storage clients and signed URLs at prototype volume.

FastAPI `BackgroundTasks` runs work after its response in the same application process. Cloud Run may shut down idle instances even with instance-based billing; changing billing mode does not make in-memory jobs durable. Therefore neither `asyncio.create_task` nor a FastAPI background callback is the substitute for Cloud Tasks here. [FastAPI background tasks](https://fastapi.tiangolo.com/tutorial/background-tasks/), [Cloud Run background execution](https://docs.cloud.google.com/run/docs/configuring/billing-settings).

Setup requires one Firebase/GCP project with billing enabled, Firebase Auth anonymous provider enabled, a Firestore database, private storage bucket, task queue, service identities/IAM, secrets, and the necessary APIs. Cloud Run's FastAPI quickstart explicitly requires billing and Cloud Run/Cloud Build APIs; source builds also use a container repository. Cloud Tasks' Cloud Run guide requires its API and queue. Choose compatible nearby locations deliberately; this is not something Firebase automatically chooses coherently for every resource. [Cloud Run prerequisites](https://docs.cloud.google.com/run/docs/quickstarts/build-and-deploy/deploy-python-fastapi-service), [Cloud Tasks setup](https://docs.cloud.google.com/run/docs/triggering/using-tasks).

Current Firebase documentation requires the **Blaze pay-as-you-go plan** for Cloud Storage for Firebase, including default buckets; the requirement is already in effect. Do not assume a Spark/free-only Firebase project is enough. Our prototype can use a backend-managed GCS bucket without the Android Firebase Storage SDK, but still needs a billed cloud project. No prices or free-tier sufficiency are estimated here. [Official Storage billing FAQ](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024).

Not checked: actual cloud-account configuration, provider idempotency/reconciliation, end-to-end latency, deployment cost or mobile behavior. The material unresolved risk is the accepted-but-unrecorded upstream submission window; the design must never promise exactly-once generation or lossless recovery without provider support.
